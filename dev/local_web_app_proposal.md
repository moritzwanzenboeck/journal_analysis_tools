# Local web app proposal

**Recommendation.** Try standalone Voilà first if the goal is to give researchers a clean interface without visible code cells or a **Run All Cells** step. Choose a local Flask app with Waitress if the browser interface is intended to become the main product. Flask takes more work up front, but gives the editor direct control over live updates and lets a future browser-app release run without Jupyter kernels. Both approaches can run on the user's machine and keep project files and pasted text there. Live journal and DOI lookups still use Crossref. [Voilà documentation](https://voila.readthedocs.io/en/stable/using.html) · [Flask deployment with Waitress](https://flask.palletsprojects.com/en/stable/deploying/waitress/)

## Options

| Option | What it hides | Fit for this repository |
| --- | --- | --- |
| **Standalone Voilà** | Hides code cells in the rendered page by default. The notebooks and Python files remain on disk. | Smallest first step. Runs the existing notebooks and keeps their widgets and callbacks. Still starts kernels. Verify clipboard, the floating preview, live headings and Safari layout before adopting it. [Voilà execution model](https://voila.readthedocs.io/en/stable/using.html#how-does-voila-work) |
| **Flask + Waitress with plain HTML, CSS and JavaScript** | Python stays on the local server. The browser receives the interface and results. Anyone who can inspect the installed files can still read shipped Python source. | Best long-term fit. Reuse the existing Python modules and project format. Rebuild the browser controls, including the stateful full-paper editor. Waitress supports Windows and can bind to loopback. [Flask deployment with Waitress](https://flask.palletsprojects.com/en/stable/deploying/waitress/) |
| **Streamlit** | Runs Python on the local server, with the source still present on disk. | Good for a quick project-creation form or read-only report. The full-paper editor would need careful handling of reruns, text focus, draft state and fixed layout. Forms and fragments can limit reruns. [Streamlit execution model](https://docs.streamlit.io/develop/concepts/architecture/session-state) |
| **Static website with JavaScript or Pyodide** | The browser receives the implementation it runs, whether as scripts or a WebAssembly runtime with Python code. | Reasonable for a standalone clean-and-count demo. Full project support would need new filesystem and network integration. Browser directory access varies, and Pyodide uses a virtual filesystem by default. [Pyodide filesystem documentation](https://pyodide.org/en/stable/usage/file-system.html) · [Browser directory picker support](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker) |

## What hiding the logic can achieve

- **Keep code out of the workflow.** Voilà can render both notebooks as forms and editors. The project writer currently embeds `clean_and_count_text.ipynb` in every generated project, so those copies remain readable even when the cells are hidden in the browser. See [the project writer](../app/journal_tools.py) and [the self-contained notebook](../clean_and_count_text.ipynb).
- **Avoid shipping readable source in a particular release.** A future browser-app-only package could compile selected Python modules and omit raw notebooks and source files from that package. It would also need an explicit project export policy for new projects, since the existing writer ships a readable notebook. Compiling adds per-platform build and signing work, and recipients can still analyze the binaries. Existing copies remain readable. [Nuitka user manual](https://nuitka.net/user-documentation/user-manual.html)
- **Keep implementation out of recipients' hands.** Running protected logic on a machine controlled by the maintainer keeps that implementation out of the local download. Any protected operation requiring paper text would send that text to the server. That option changes the local and offline requirements and merits a separate decision.

## Pilot and acceptance checks

1. **Run both notebooks in standalone Voilà.** Add an opt-in launcher path for the pilot. Serve specific notebook views, open the authenticated loopback URL after readiness, and verify that stopping the service also stops its kernels. Test clipboard behavior, Markdown heading edits, preview dismissal and summary sizing in Chromium and Safari. Keep the Chromium regression check that removes `AbortSignal.any`. See [the launcher service](../app/notebook_services.py) and [the browser check](check_paper_layout.py).
2. **If a dedicated app is the goal, build the browser interface around the existing Python functions.** Start with clean-and-count, then add random and manual project creation. Leave full-paper editing and the project summary until the basic launch and file round trip work. Use `app/text_tools.py`, `app/journal_tools.py` and `app/paper_tools.py` for the rules, a native folder chooser for project access, and debounced requests for live counts and heading edits. Scope file operations to the selected project or projects parent. Verify that late responses cannot replace newer edits. Serve the pages and API from the same authenticated loopback origin. Keep the notebook workflow available during the pilot and use the existing fixtures to check parity.
3. **Check parity before changing distribution.** Read `project.json` and its `sample_export` CSV, reopen legacy JSON, and write cleaned text and assignments to `paper_categorizations/`. Check offline archive replay, project creation without overwrites, DOI deduplication and cached retries, exports from checked metadata without another fetch, transactional category removal, and latest-per-DOI summary behavior. Bundle dependencies at build time. Verify startup and shutdown on Windows, Intel Mac and Apple Silicon using the bundled runtime, including Finder launch from the signed Mac app. Review generated project contents explicitly if a later release aims to omit readable source.
